# SWAY — Backend-first starter

This repository is the backend foundation for **Sway**, an anonymous campus/community
confessions and connections app. It is an AI-coding handoff pack, not a claim that the
service is production-ready.

## Stack
- Cloudflare Workers + Hono + TypeScript
- Supabase PostgreSQL + Supabase Auth (anonymous sessions) + Realtime
- Cloudinary for media (signed upload parameters generated by the Worker)
- Zod for request validation
- Expo Android app and iOS-installable PWA are planned as separate frontend clients.

## Important corrections to the earlier sketch
1. A client-generated `device_id` is not authentication. It can be copied or spoofed.
   This starter uses Supabase anonymous authentication and validates the Supabase access
   token on every protected API request.
2. Never put the Supabase `service_role` key or Cloudinary API secret in the app or
   `wrangler.toml`. Set them as Worker secrets.
3. Row Level Security (RLS) is enabled in the SQL migration. Do not disable it.
4. A regex word list is not content moderation. This starter includes report/block flows
   and leaves automated moderation as a replaceable integration point.
5. Do not launch anonymous messaging/posts without moderation, abuse reporting, blocking,
   rate limits, retention rules, and a human escalation process.

## Setup Instructions

### Prerequisites
- Node.js 18+ and npm
- A Supabase project
- A Cloudinary account
- Wrangler CLI (`npm install -g wrangler`)

### Step 1: Create Supabase Project
1. Go to [supabase.com](https://supabase.com) and create a new project
2. Note your project URL and anon key from Project Settings → API

### Step 2: Run Database Migrations
1. In Supabase SQL Editor, run migrations in order:
   ```sql
   -- First, run supabase/migrations/0001_initial_schema.sql
   -- Then, run supabase/migrations/0002_accept_connection_rpc.sql
   ```

2. In Supabase Auth settings:
   - Enable **Anonymous sign-ins**
   - Configure allowed origins before production deployment

3. In Supabase Database → Replication → Publications:
   - Verify `supabase_realtime` publication includes the `messages` table

### Step 3: Configure Cloudinary
1. Get your Cloud Name, API Key, and API Secret from your Cloudinary dashboard
2. Create an unsigned upload preset:
   - Go to Settings → Upload → Upload presets
   - Click "Add upload preset"
   - Set to "Unsigned" mode
   - Configure folder prefix, allowed formats, file size limits
   - Note the preset name

### Step 4: Install Dependencies
```bash
npm install
```

### Step 5: Configure Local Development
1. Copy `.dev.vars.example` to `.dev.vars`:
   ```bash
   cp .dev.vars.example .dev.vars
   ```

2. Edit `.dev.vars` and add your secrets:
   ```
   SUPABASE_ANON_KEY=your_supabase_anon_key_here
   CLOUDINARY_API_SECRET=your_cloudinary_api_secret_here
   ```

3. Edit `wrangler.toml` and update these values:
   ```toml
   [vars]
   SUPABASE_URL = "https://your-project-ref.supabase.co"
   CLOUDINARY_CLOUD_NAME = "your-cloud-name"
   CLOUDINARY_API_KEY = "your-cloudinary-api-key"
   CLOUDINARY_UPLOAD_PRESET = "your-upload-preset-name"
   ALLOWED_ORIGINS = "http://localhost:8081,http://localhost:5173"
   ```

### Step 6: Run Locally
```bash
npm run dev
```

Your API will be available at `http://localhost:8787`

Test the health endpoint:
```bash
curl http://localhost:8787/health
```

### Step 7: Deploy to Production

1. Set production secrets:
   ```bash
   npx wrangler secret put SUPABASE_ANON_KEY
   # Paste your Supabase anon key when prompted

   npx wrangler secret put CLOUDINARY_API_SECRET
   # Paste your Cloudinary API secret when prompted
   ```

2. Update production origins in `wrangler.toml`:
   ```toml
   ALLOWED_ORIGINS = "https://your-production-domain.com"
   ```

3. Deploy:
   ```bash
   npx wrangler deploy
   ```

4. Note the deployed Worker URL (e.g., `https://sway-backend.your-subdomain.workers.dev`)

5. Update Supabase Auth allowed origins:
   - Go to Supabase → Authentication → URL Configuration
   - Add your Worker URL to allowed redirect URLs

## API Overview
See `docs/API_CONTRACT.md` for complete API documentation.

Key endpoints:
- `GET /health` - Health check (no auth required)
- `GET /api/me` - Get/create user profile
- `POST /api/posts` - Create a post
- `GET /api/posts` - Get paginated feed
- `POST /api/connections` - Send connection request
- `PATCH /api/connections/:id` - Accept/reject connection (creates conversation)
- `GET /api/conversations` - List conversations
- `POST /api/conversations/:id/messages` - Send message
- `POST /api/reports` - Report content
- `POST /api/blocks` - Block user
- `POST /api/uploads/sign` - Get Cloudinary upload signature

All `/api/*` routes require `Authorization: Bearer <supabase_access_token>`.

## Realtime Setup
Enable the `messages` table in Supabase Realtime publication. Clients subscribe only to
their own conversation messages. Realtime is a delivery mechanism, not an authorization
boundary; RLS still applies.

Example client subscription:
```javascript
const channel = supabase
  .channel('conversation-messages')
  .on('postgres_changes', {
    event: 'INSERT',
    schema: 'public',
    table: 'messages',
    filter: `conversation_id=eq.${conversationId}`
  }, (payload) => {
    console.log('New message:', payload.new);
  })
  .subscribe();
```

## What's Implemented

✅ **Security:**
- Supabase anonymous auth validation on every request
- RLS enabled on all tables with proper policies
- Request body size limits (100KB max)
- Input validation with Zod schemas
- Proper error handling and mapping
- Cloudinary upload restrictions (5MB, jpg/png/webp only)
- User-owned folder validation for uploads

✅ **Features:**
- Profile management with unique usernames
- Post creation and feed with pagination
- Connection requests with transactional acceptance
- Automatic conversation creation on connection accept
- Messaging within conversations
- Content reporting
- User blocking with feed filtering

✅ **Code Quality:**
- TypeScript with strict mode
- Modular route structure
- Comprehensive type definitions
- Structured error responses

## Known Limitations

This is a backend milestone implementation, not a production-ready service:

- No rate limiting active yet (infrastructure in place)
- No automated content moderation
- No admin dashboard
- No account recovery mechanism
- No data export functionality
- Block enforcement in messages needs per-message validation
- No performance/load testing completed

See the audit document for a complete list of remaining work before launch.
